## 原因

run.bat 原来用 `py -3` 找 Python。`py -3` 给的是这台电脑上**最新**的 Python —— CI 的 Windows 机器上
除了我们指定的 3.11，还装着更新的版本（推断是 3.14：日志里没打印用的哪个，这一次起会打印）。
而原来钉的版本**在 3.14 上没有 Windows 预编译包（wheel）**，逐个查过：

| 包（原来钉的版本） | 3.11 | 3.12 | 3.13 | 3.14 |
|---|---|---|---|---|
| numpy 2.2.1 / pandas 2.2.3 / pydantic-core 2.27.2 / Pillow 11.1.0 | ✅ | ✅ | ✅ | ❌ 全都没有 |

没有 wheel，pip 就下载源码自己编译；numpy 编译要 C 编译器和几分钟到几十分钟，**一般人的电脑上没有编译器，就一直卡在那一行**。

**这不只是 CI 的问题**：README 叫同事「到 python.org 下载安装」—— 现在 python.org 首页给的是 **3.15**。
照着做的人双击 run.bat 会卡在同一个地方。

## 做了什么

**1. 依赖升级到在 3.11 – 3.15 上都有 Windows wheel 的版本**（每个版本 × 每个 Python 逐一查过，
并用 `pip install --dry-run --only-binary=:all: --platform win_amd64` 把**整棵依赖树**在 5 个版本上都解析了一遍，全部通过）

| 包 | 原来 | 现在 |
|---|---|---|
| fastapi | 0.115.6 | 0.162.0 |
| uvicorn | 0.34.0 | 0.54.0 |
| pydantic | 2.10.4 | 2.14.3 |
| python-multipart | 0.0.20 | 0.0.33 |
| **pandas** | 2.2.3 | **3.1.1**（大版本；3.1 是第一个有 3.15 wheel 的） |
| **numpy** | 2.2.1 | **3.11 上 2.4.6，3.12 起 2.5.4** —— 没有一个版本同时覆盖 3.11 和 3.15（2.5 不再支持 3.11，2.4 没有 3.15 的 wheel），所以按 Python 版本分两行 |
| Pillow | 11.1.0 | 13.0.0 |
| openpyxl / httpx | 3.1.5 / 0.28.1 | 不变 |
| （开发用）pytest / matplotlib | 8.3.4 / 3.11.1 | 9.2.0 / 3.11.2 |

pandas 3 的两处行为变化逐个查过：
- **Copy-on-Write**（链式赋值不再写回原表）：代码里没有这种写法
- **文本列默认是 `str` 类型，空格子是 NaN 而不是 None**：唯一受影响的是表格预览的空格子。实测预览接口在新旧版本下都返回 `null` ——
  靠的是路由标了 `-> dict`，FastAPI 按 pydantic 的 JSON 模式输出，把 NaN 变成 null。我一开始以为这里有 500 的 bug，
  在**原来的依赖版本**下也复现了一遍，确认不是 bug，所以没改代码，只补了一条测试把这个行为钉住（数值列、文本列都有空格子，外加 `inf`）

**2. run.bat / run.sh 挑 Python 的方式**
- 不再用 `py -3`：从 3.15 到 3.11 **从新到旧**挑第一个装了的（`py -3.15`、`py -3.14` …），都没有再试 `python`，并检查版本在范围内
- 第一行打印用的是哪个：`使用 Python 3.13.1（py -3.13）`
- 找不到时，告诉你这台电脑上的 `py -3` / `python` 实际是什么版本、为什么不能用，叫你装 3.13
- 已有的 `.venv` 如果是用不在范围内的 Python 建的，自动重建（以前只检查它能不能跑）
- 装依赖加 `--only-binary=:all:`：**只装预编译包**。哪个依赖没有 wheel，立刻报错，而不是在没有编译器的电脑上编译到天荒地老。
  报错文字里加了第二个常见原因「这个 Python 版本太新」

**3. 守住它**
- CI 的 Windows 测试加一个 **3.15**（范围的两头 3.11 和 3.15 都测），CI 装依赖也加 `--only-binary=:all:` —— 以后升级依赖，哪个版本没有 wheel 当场就红
- 新增 `tests/test_launchers.py`（3 条）：run.bat、run.sh、requirements.txt、CI 矩阵**说的是同一个版本范围**；两个启动脚本装依赖都带 `--only-binary`；run.bat 是 CRLF 换行
- 新增 `.gitattributes`：`.bat` 检出为 CRLF、`.sh` 为 LF（cmd 解析 LF 换行的批处理有已知的怪毛病；这次改 run.bat 时我自己的工具就把它存成了 LF，测试当场抓到）
- requirements.txt 开头写明：改任何版本号之前怎么查 wheel、上限改了要同步改哪几处

**4. 文档**：README「跑起来需要什么」改成「Python 3.11 到 3.15，拿不准就装 3.13」，并说明比 3.15 新的为什么不用；Windows 实机清单第 1 步加上「先显示用的哪个 Python」。

**已经在用的人**：requirements.txt 变了，下次双击 run.bat 会自动重装一遍依赖（约 1 分钟），pandas 随之升到 3。数据不动。

## 我自行决定的
- **D-80** 支持的 Python 定为 **3.11 – 3.15**，启动脚本从新到旧挑范围内的；提示里推荐装 **3.13**（成熟、所有依赖都早就有 wheel）。
  范围的上限是「当前所有依赖都出了 wheel 的最新版」，以后升级依赖时一起往上挪
- **D-81** 依赖整体升级，含 **pandas 2.2 → 3.1（大版本）**，numpy 按 Python 版本分两个版本号（**建议你确认** —— 数据处理库的大版本升级。
  所有数值测试（膜厚算法回归、前后端算子逐点比对、批处理长表、迁移）在 3.11 和 3.13 上全部通过、结果不变；但你自己的数据在新版本下若有任何数对不上，请告诉我）
- **D-82** 启动脚本和 CI 都只装预编译包（`--only-binary=:all:`）：宁可马上报错也不编译
- **D-83** CI Windows 测试改成测范围两头（3.11 + 3.15）；版本范围四处一致由测试守着；`.gitattributes` 固定换行
