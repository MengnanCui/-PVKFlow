## 做了什么
- 问题：`write_file` 用 find / replace 改一个**没有 BOM 的 UTF-8 文件**，写回去时开头多了三个字节的 BOM（`EF BB BF`）。
  原因：平台的解码器按 `utf-8-sig → utf-8 → gb18030 → latin-1` 依次试，`utf-8-sig` 也能解没有 BOM 的文件，于是被当成「原编码」写回。
  有的程序（老的 CSV 读取、脚本解释器）看到 BOM 会把第一列名读错
- 修法：原文没有 BOM 就按 `utf-8` 写回；有 BOM 的照样保留；GB18030、UTF-16 都按原编码写回
- 解码只能退到 latin-1（也就是认不出编码）的文件：**不按文本改**，说清楚原因 —— 按 latin-1 写回去会把没动的那部分也弄坏
- 新测试：UTF-8、带 BOM 的 UTF-8、GB18030、UTF-16 四种文件改一段之后，**字节**和预期完全一致

## 用户明确指定的参数
- 无

## 我自行决定的
- **D-150** 改文件时保持原编码，不凭空加 BOM；认不出编码（只能当 latin-1 解）的文件不按文本改

## 遗留 / 没做的
- 换行符（CRLF / LF）按模型给的原样写：find / replace 只动那一段，整文件重写时如果模型给的是 LF，原来是 CRLF 的文件会变成 LF
