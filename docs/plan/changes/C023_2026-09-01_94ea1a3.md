## 当时的说明（原文）

chart.js 的 viewBox 写死 760 宽、heatmap.js 写死 900，而 CSS 是
.chart-host svg { width: 100% } —— 整张图连字一起被容器宽度缩放。
同一句 font-size: 11 于是渲染成完全不同的大小：

  样品页 · 模块曲线   viewBox 760，容器 530px，0.70×  →  7.7px
  样品页 · 热力图     viewBox 900，容器 530px，0.59×  →  6.5px
  对比页 · 叠图       viewBox 760，容器 1190px，1.57× → 17.2px

一边小得看不清，一边大得突兀。而图注是 HTML、在 SVG 外面，真的是 11px ——
所以同一张图里，下面的图注和上面的坐标轴刻度差了三分之一。

改法：viewBox 的宽度设成容器的实际像素宽，缩放恒等于 1。写 11 就是 11，
在哪个页面、哪个屏宽下都一样。三个图表函数共用一个 trackWidth()：
ResizeObserver + rAF 合并，8px 以内不重画（滚动条出现消失会让宽度抖一两像素，
跟着抖就是每帧重建骨架）。barChart 原来是一条直线画完的，顺手包成 draw()。

高度也跟着变对了 —— 以前那个值同样被缩放吞掉。按你定的调到 250 一档：
Panel.height 默认 300→250，样品页叠加谱 340→280，对比页 340/320→300。
样品页的图从 209px 变成 250px，对比页那种 532px 的巨图收回 300px。

一个中途踩到的坑：本来想让刻度数量跟着宽度走（窄图少画几个），
结果 niceTicks 会把轴两端扩到步长的整数倍 —— 刻度少 → 步长粗 → 轴被撑爆。
波长轴 422–1120 在 3 个刻度时步长变 500、轴变成 0–1500，**一半以上的画布是空的**。
所以 tickCount 的下限钉死在原来的密度（x 5 个、y 5 个），它只用来给宽图**加**刻度。

实测：四张图现在 scale 全是 1.00，声明 11px、渲染 11px。

代价：拖动 → 曲线更新，同机对照 HEAD 4.2/4.2/4.3 ms，新版 4.4/4.5/4.5 ms。
差的这 0.3ms 不是 ResizeObserver 带来的（临时关掉它并不会变快），
是图变高之后的自然开销，也在逐次波动范围内（两版单次都在 3.1–4.8 之间）。
悬停仍是 0.1ms / 7–29 节点。AI 抽屉开合从 2/124 帧超 20ms 变成 5/121 ——
比加宽度过渡那次的 22/112 好得多，可以接受。

图表交互 18 项、热力图 11 项、换参数 8 项、动画 8 项全过，330 项 pytest 全绿。
