## 当时的说明（原文）

「为什么占用空间这么大」—— 量了一下，占地方的**不是数据，是依赖**：
用户装完 .venv 372 MB，而三个样品的 workspace 才 9.3 MB。

**pyarrow：131 MB，占整个安装的三成，从必装清单里拿掉**

算一笔账：一次 40 样品的批处理长表，
    Parquet 0.05 MB / 写 122ms / 读 78ms
    CSV     0.63 MB / 写  42ms / 读 18ms
省 0.58 MB，代价是 131 MB —— 要跑两百多次批处理，省下的体积才抵得上
它自己的安装体积，而且这个规模下它读写还更慢。

原来那句「第三期上 DuckDB 时可以直接 SELECT * FROM 'tables/*.parquet'」
是拿将来的好处为现在的 131 MB 买单，何况 DuckDB 读 CSV 一样。
真要上的时候 pip install pyarrow 即可，代码里那条分支一直留着，
装了就自动改用 Parquet。

**uvicorn[standard] → uvicorn：19 MB**
那个 extra 拖进 uvloop(14MB) + httptools + watchfiles + websockets，
grep 下来一个都没用到。本地单用户、一个浏览器，纯 asyncio 够了。

**补上缺失的测试**
tabular.py 里「pyarrow 缺失时退回 CSV」的分支从**兜底**变成了**默认路径**，
而它一直没有测试。补两条：一条测 tabular 本身，一条走完整条批处理链路 ——
真正会坏的是「写的时候退回 CSV、读的时候还按 Parquet 读」这种两头对不上，
只测写入侧看不出来。

**验证**（都是干净安装实测，不是估的）
- 新 requirements 干净装：219 MB；加回那两项：372 MB
- 在真的没有 pyarrow 的环境里跑全量测试：244 passed, 3 skipped
  （跳过的是 matplotlib 导出测试，那本来就是 dev 依赖）
- 在同一个环境里起服务、导入 3 个样品、跑一次批处理：
  长表落成 batch_curves__*.csv，对比页正常读回

README 补了「会占多大」一节。之前只写了 workspace 的 1.4 倍，
完全没提装机体积 —— 而那才是用户真正会注意到的那个数字。
测试 245 → 247。
