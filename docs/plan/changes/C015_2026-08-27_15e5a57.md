## 当时的说明（原文）

**★ 一、所有页面首屏以下的内容都够不着**

.main 的 grid-template-rows 写的是 `var(--topbar-h) 1fr`。
`1fr` 的完整含义是 `minmax(auto, 1fr)` —— 行的**最小**高度是内容高度。
于是 .viewport 被内容撑到 2000 多像素，它的 overflow:auto 永远不触发，
再被 .shell 的 overflow:hidden 一剪，下面的东西就彻底没了。

实测（800px 窗口）：设置页内容 2213px、能滚 = false；数据存储 1071px、
能滚 = false。总览页正好 740px 装得下一屏，所以这个 bug 藏了很久。

改成 `minmax(0, 1fr)` + min-height: 0。修完：视口 740、内容 2213、
滚到 1473 ✓。

为什么演示版没露馅：打包脚本注入了 `html,body{height:auto}` 和
`.viewport{overflow:visible}`，把这套布局整个覆盖掉了。已在 assemble.py
里写明这一点 —— **布局问题一律以 run.bat 起的真实应用为准**。

**★ 二、「不像光谱矩阵：只有 9 行 × 2 列」**

那 9 行正是 Data.csv 的抬头。链条是：looks_like_insitu 判假 → 退回普通
宽表 → pandas 拿 2 格的抬头当表头 → 几百格的数据行被 on_bad_lines="skip"
全部丢掉 → 剩下 9 行 × 2 列。

根因不是某一条判断写错，而是**判定认名字不认结构**：要求首格字面上以
"Wavelength" 结尾、时间行必须精确等于「相对第一帧时间(s)」、分隔符写死 \t。
这是把手上那一份样本当成了格式定义。

改成认结构：
- 块头 = 非数字首格 + 很多格（名字被分隔符切开、大小写不同都认）
- 时间行 / 采集时间行走正则（全角括号、英文都认）
- 分隔符按「哪个能切出最多格」猜（逗号、分号都认）
- 编码先认 UTF-16（Windows 仪器软件常写 UTF-16LE）。这条单独说：
  latin-1 对任何字节都不报错，所以候选列表里有它的话，UTF-16 文件会被
  「成功」解成夹着 NUL 的乱码 —— 不崩不报错，只是所有字符串比较都对不上。

判定还必须要求一条原位格式**独有**的特征（块内时间行，或块前两格的
key/value 抬头）—— 只看「块头 + 数据行」的话普通光谱宽表长得一模一样，
会被全部误判（第一版就这么干的，26 个 test_spectra 当场变红）。

两条底线没有放宽：
- 只剩 Origin 块时**仍然报错**，不拿它顶替（原始 PD 计数，量纲量级都不对）
- 既没有相对时间行也没有采集时间时**仍然报错**，不拿帧序号编一条充数
  （横轴写着「时间 (s)」，编出来的轴会让每张膜厚曲线都在撒谎）。
  但能从采集时间推的时候就推 —— 那是文件里真有的信息，并在元信息里注明来路。

**解析失败时报错带上文件结构速写**（每行首格 + 格数 + 猜到的分隔符）。
上一版只说「不像光谱矩阵」，你没法自查，我这边也无从判断是分隔符、编码
还是块名的问题 —— 错误信息本身就该是排查通道。

测试 233 → 245：10 种格式变体逐一跑完整链路（UTF-16 / BOM / CRLF /
块名被切开 / 小写 / 全角括号 / 英文行名 / 逗号 / 分号 / 陌生抬头字段）。
浏览器实跑：12 个变体全部通过界面按子文件夹导入，样品页出 1028λ × 211 帧。
